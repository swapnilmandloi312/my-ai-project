# Private cloud operations read model (v0.26 candidate)

This prepares a read-only founder reporting database, not the execution queue. No live Supabase project is connected. The migration has three prefixed tables: tenants, memberships and verified operations run records. Authenticated browser users may SELECT only their own tenant's records; membership and data ingestion are trusted server-side administration only. Do not expose the service_role credential; it bypasses RLS. Report summary is potentially private: publish neither data nor credentials in GitHub or public static assets. Keep trusted ingestion identity separate from the browser. A unique tenant/source/run identifier avoids duplicate records. Timestamps and explicit statuses distinguish schedules from recorded execution; the database cannot independently verify source evidence.

CI uses PostgreSQL 16 with simulated auth roles and auth.uid(), not live Supabase Auth, PostgREST, JWT validation or production credentials. Only 001_private_operations.sql is a candidate migration; NEVER run test_bootstrap.sql or test_isolation.sql in a real project. Production gate: connect the owner-authorized Supabase project, inspect existing schema and grants, review migration, create private staging tenant, configure real Auth and explicit membership, test two signed-in accounts and anonymous REST denial, add trusted authenticated ingestion with rate/size limits and credential rotation, define retention and backups, then connect a private dashboard read API and verify hosted data. Do not enable remote agent writes until a separately tested transactional queue, operator authorization and incident controls exist. Current SQLite job broker is not migrated by this schema. No paid services, account changes or data uploads from this candidate. Keep hosted Vercel dashboard unchanged until acceptance.
